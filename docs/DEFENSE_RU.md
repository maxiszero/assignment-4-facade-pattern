# Подготовка к защите Assignment 4 Facade Pattern

## Объяснение за 40 секунд

«Я выбрал предложенную тему Home Theater. Для просмотра фильма нужно согласованно
настроить пять подсистем: свет, экран, DVD-плеер, усилитель и проектор. Например,
проектор требует опущенный экран и работающий плеер. HomeTheaterFacade скрывает
этот порядок за watchMovie и endMovie. Main использует только фасад. Подсистемы
хранят собственное состояние, проверяют условия работы и ничего не знают о фасаде.
Опытный клиент может использовать их напрямую. Если запуск завершается ошибкой,
фасад выполняет очистку и сохраняет причину ошибки».

## Что делает каждый класс

| Класс | Ответственность |
| --- | --- |
| `Main` | Обычный клиент: вызывает только публичный API фасада. |
| `HomeTheaterFacade` | Согласует запуск, завершение и восстановление сеанса. |
| `DvdPlayer` | Загружает и нормализует название фильма, управляет воспроизведением и извлечением. |
| `Projector` | Проверяет плеер и экран, хранит источники изображения и состояние проекции. |
| `Amplifier` | Проверяет активный источник звука и допустимую громкость. |
| `Screen` | Хранит положение экрана: поднят или опущен. |
| `Lights` | Проверяет и хранит яркость от 0 до 100. |
| `TheaterOperationException` | Сообщает об ошибке координации, сохраняя исходную причину. |

Это модель домашнего кинотеатра в памяти. Программа не воспроизводит видеофайлы
и не подключается к реальному оборудованию. Логика подсистем реальная для этой
модели: состояния и ограничения проверяются программно, а не только печатаются.

## Порядок действий

При `watchMovie(title)` сначала проверяются название и готовность сеанса. Затем
фасад запоминает яркость комнаты, загружает фильм, устанавливает яркость 20,
опускает экран, запускает плеер, подключает усилитель с громкостью 30 и включает
проекцию. Только после успеха всех шагов состояние становится `WATCHING`.

При завершении сначала останавливаются проектор и усилитель, затем плеер.
После этого фильм извлекается, экран поднимается, а первоначальная яркость
восстанавливается. Поэтому `eject()` не вызывается у играющего плеера.

## Демонстрация на защите

1. Покажи UML: `Main` обращается к фасаду; фасад хранит пять подсистем; проектор
   и усилитель используют плеер, а проектор дополнительно использует экран.
2. Открой `Main.java`: там нет создания или вызовов классов подсистем.
3. Покажи `watchMovie`: один вызов клиента превращается в согласованный сценарий.
4. Открой `Projector.start`: неправильный порядок приведёт к исключению, поэтому
   фасад действительно выполняет полезную координацию.
5. Запусти `powershell -ExecutionPolicy Bypass -File .\build.ps1 demo`.
   Покажи `Ready`, `Watching: Interstellar`, отказ повторного старта, завершение
   и новый сеанс с `Dune`.
6. Запусти `powershell -ExecutionPolicy Bypass -File .\build.ps1 test`.
   Ожидаемый результат — `PASS: 16 tests`.
7. В тестах покажи `advanced clients can operate all five subsystems directly`,
   затем тесты отказа проектора и повторной очистки.

Для другого названия после сборки:

```sh
java -cp build/classes theater.Main "The Lord of the Rings"
```

## Возможные вопросы

**Что такое Facade?** Структурный паттерн, предоставляющий простой интерфейс
для типичных задач сложной подсистемы.

**Где здесь сложность?** Есть пять объектов и требования к порядку. Усилитель
и проектор требуют активного плеера; проектор дополнительно требует опущенный
экран; перед извлечением фильма нужно остановить воспроизведение. Также нужно
правильно завершать частично начатый сеанс при сбое.

**Что фасад скрывает?** Создание подсистем, их связи, порядок вызовов, стандартные
уровни яркости и громкости, завершение и восстановление после сбоя. Публичные
методы возвращают только понятный статус или принимают название фильма.

**Почему подсистемы public?** Facade упрощает обычный сценарий, но не запрещает
расширенный доступ. В задании прямо требуется возможность обходить фасад.

**Откуда видно, что подсистемы не знают о фасаде?** В `theater.subsystem` нет
полей, параметров, импортов или вызовов `HomeTheaterFacade`. Зависимость направлена
от фасада к подсистемам. Между самими подсистемами связи допустимы.

**Почему это не просто класс со множеством методов?** Фасад использует готовые
операции подсистем и координирует их. Он не реализует внутри себя логику всех
устройств. Проверка громкости остаётся в `Amplifier`, а правила воспроизведения —
в `DvdPlayer`.

**Чем Facade отличается от Bridge из прошлого задания?** Bridge разделяет две
изменяемые стороны, например фигуры и способы рисования. Facade предоставляет
одну удобную точку входа для нескольких взаимодействующих компонентов.

**Чем отличается от Adapter?** Adapter согласует несовместимые интерфейсы.
Facade делает использование подсистемы проще, объединяя последовательность
операций в более крупный сценарий.

**Чем отличается от Mediator?** Компоненты Mediator знают посредника и общаются
через него. Здесь подсистемы не знают фасад и могут взаимодействовать напрямую.

**Нужен ли Singleton?** Нет. Singleton управляет количеством экземпляров.
Facade упрощает интерфейс. Можно создать отдельный фасад для каждой комнаты.

**Что будет при втором watchMovie?** Если сеанс уже активен или требуется очистка,
возникнет `IllegalStateException`. Текущий фильм не будет заменён.

**Зачем повторный endMovie безопасен?** Если сеанс уже завершён, метод ничего не
делает. Это удобно для вызывающего кода: повторная команда завершения допустима.

**Что произойдёт при отказе проектора?** Фасад попробует остановить все устройства,
извлечь фильм, поднять экран и вернуть прежнюю яркость. Затем выбросит
`TheaterOperationException` с исходной причиной в `getCause()`.

**А если очистка тоже сломалась?** Остальные шаги всё равно выполняются. Ошибки
не теряются: дополнительные доступны через suppressed exceptions. Состояние
остаётся `CLEANUP_REQUIRED`; новый фильм запрещён. Можно повторить `endMovie()`.

**Это транзакция с гарантированным rollback?** Это компенсирующие операции.
Они могут завершиться ошибкой, что программа явно сообщает. Здесь нет гарантии
атомарности или управления настоящим оборудованием.

**Зачем package-private конструктор с подсистемами?** Для тестов можно передать
заранее созданные компоненты и неисправный проектор. Обычный клиент использует
публичный конструктор без параметров; типы устройств не попадают в публичный API.

**Почему Projector не final?** Тесты создают вариант проектора с отказом, чтобы
проверить очистку. Остальные компоненты используются в настоящей реализации.
Для большого проекта альтернативой мог бы стать отдельный интерфейс устройства.

**Какие шесть принципов Clean Code показаны?** Понятные имена, единая
ответственность фасада, сокрытие деталей, небольшие сфокусированные подсистемы,
явная обработка ошибок, повторное использование общей логики очистки.

**Какие недостатки?** Фасад связан с пятью конкретными классами и предоставляет
стандартный сценарий с фиксированными настройками. Он может разрастись, если
добавлять несвязанные функции. Модель рассчитана на один поток выполнения.
